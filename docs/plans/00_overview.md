# 実装計画 概要

`docs/idea` の内容をもとに、CANSHI の実装を PR 単位に分割した計画書。各ファイルは 1 つの PR に収まる粒度を目安にしている。

- MVP（`01`〜`15`）は 1 ファイル 1 PR として詳細化する
- 第2段階は `16` に概要を記載し、`18`〜`31` で 1 ファイル 1 PR として詳細化する
- 第3段階は `17` に概要レベルでのみ記載し、詳細化は別途行う
- デプロイ手順（Cloudflare Workers への公開、環境変数、シークレット管理など）はこの計画のスコープ外とし、`docs/deploy.md` にまとめる

## フェーズの判断基準

`docs/idea/index.md` の「機能一覧」にはすべての段階の機能がまとめて記載されているが、実装順序は「開発方針」の MVP / 第2段階 / 第3段階の区分を優先する。具体的には次の機能は MVP に含めない。

- 写真・動画のアップロードおよび配信（うんち・嘔吐・症状・服薬・通院・愛猫の体の「写真を記録」はすべて第2段階以降）
- 水・シャンプー・掃除の記録
- 通知（誕生日等の通知、通知センター）
- PWA、Web Push
- AI による画像の補助分類、AI 参照用プロフィール
- 複数猫の切り替え UI・猫ごとの比較（DB は最初から複数猫対応にしておく）

この判断に異論がある場合は、対象 PR に着手する前に確認してください。

## 前提として決定した技術選定

計画を書き進めるうえで、`docs/idea` に明記がなかった以下の項目は暫定的に決定した。異論があれば該当 PR の着手前に変更可能。

- パッケージマネージャ：pnpm
- ORM／マイグレーション：Drizzle ORM + Drizzle Kit（Cloudflare D1 と `wrangler d1 migrations` の相性がよいため）
- E2E テストツール：Playwright（`01` でセットアップし、最初の記録入力シナリオは `08` で実装する）
- ローカル開発：`docker compose up` で `wrangler dev`（D1・R2 のローカルエミュレーション込み）を起動する

## スキーマの前方互換方針

- すべての記録テーブルは最初から `cat_id` を持つ（`docs/idea/index.md` の方針どおり）
- 第2段階で追加される画像・動画添付、第3段階で追加される AI 補助分類についても、`03` で以下のテーブルを MVP の時点で用意しておく
  - `media_assets` テーブル：画像・動画を一元管理する正規化テーブル。`record_type` + `record_id` で対象の記録（うんち・体重・嘔吐・症状・服薬・通院など）に紐付ける。個別の記録テーブルに画像用のカラムは追加しない
  - `ai_evaluations` テーブル：AI 評価結果を一元管理する正規化テーブル。同じく `record_type` + `record_id` で対象レコードに紐付ける
- ただし MVP の UI・API では画像アップロードや AI 評価の呼び出しは実装しない（テーブルのみ用意し、書き込みは第2・第3段階の PR で行う）

## 症状・服薬・通院の紐付け順序

3 つの記録は相互に参照し合う仕様（症状⇄服薬、症状⇄通院、服薬⇄通院）のため、循環依存を避けて次の順序で実装する。

1. `11` 症状記録：単独で完結させ、他レコードへの参照列は追加しない
2. `12` 服薬記録：症状記録への外部キー（nullable）を追加する
3. `13` 通院記録：症状記録・服薬記録への外部キー（nullable）を追加すると同時に、症状記録・服薬記録に通院記録への外部キー（nullable）を後付けするマイグレーションを含める

## タイムラインの実装方針

各記録テーブルは代表となる発生日時の列を 1 つ持つ（列名はテーブルのドメインに合わせてよい。対応表は `03` に記載）。`14` のタイムライン機能はこの対応表に従って各テーブルを `UNION ALL` で集約する。個別の記録機能 PR（`07`〜`13`）は対応表に列を追加するだけでよく、タイムライン機能の実装を待つ必要はない。第2段階で追加する記録テーブル（`22`・`24`〜`26`）も同じ方針で対応表に追記し、タイムラインに集約する。
